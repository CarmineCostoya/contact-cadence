# Contact Cadence Database Schema

Contact Cadence uses PostgreSQL. A user owns contacts and tags. Contacts own interactions, while junction tables connect contacts to stars and tags.

```text
users 1 ─── * contacts 1 ─── * interactions
  │              │
  │              * ─── * tags, through contact_tags
  └────────────── * stars * ───────────── contacts
```

## Tables

### `users`

- `id`: integer primary key, generated by PostgreSQL
- `email`: required unique text, normalized to lowercase
- `password_hash`: required text; the original password is never stored
- `created_at`: timestamp

### `contacts`

- `id`: integer primary key
- `user_id`: required foreign key to `users.id`
- `name`: required text
- `organization`, `role`, `how_met`, `notes`: optional text
- `met_on`, `next_follow_up_on`: optional calendar-only dates
- `created_at`, `updated_at`: timestamps

Deleting a user deletes their contacts. Deleting a contact also deletes its interactions, stars, and tag assignments.

### `interactions`

- `id`: integer primary key
- `contact_id`: required foreign key to `contacts.id`
- `interaction_type`: required text limited to Meeting, Coffee chat, Call, Message, Email, Event, or Other
- `occurred_on`: required date
- `notes`: optional text
- `created_at`: timestamp

One contact can have many interactions.

### `stars`

- `id`: integer primary key
- `user_id`: required foreign key to `users.id`
- `contact_id`: required foreign key to `contacts.id`
- `created_at`: timestamp

The user/contact pair is unique, so the same user cannot star one contact twice. This is the required junction table connecting users and items.

### `tags`

- `id`: integer primary key
- `user_id`: required foreign key to `users.id`
- `name`: required text, unique per user without regard to capitalization
- `created_at`: timestamp

### `contact_tags`

- `contact_id`: foreign key to `contacts.id`
- `tag_id`: foreign key to `tags.id`
- The two columns together are the primary key.

This table creates the many-to-many relationship: one contact can have many tags, and one tag can belong to many contacts.

### `user_sessions`

Created and maintained by `connect-pg-simple`. It stores the random session ID, encrypted/signed session data, and expiration time so a login can survive a server restart.

## Privacy Rule

The browser never supplies a trusted user ID. The server reads the authenticated user ID from the HTTP-only session cookie, and every contact query includes that ID. Nested interaction and tag routes first verify ownership of the parent contact.
