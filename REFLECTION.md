## Reflection 1 — The biggest gap between the plan and the shipped app

The largest gap between my original plan and the final implementation was the production architecture. In the original [`PLAN.md`](./PLAN.md), I proposed a Node/Express backend, password hashing with `bcryptjs`, server-side sessions, and a Replit-managed PostgreSQL database. That design matched the full-stack pattern I initially understood, but I discovered during deployment that keeping an active Replit server and database could create a compute charge. Because I wanted the assignment to remain free to host, I changed the architecture rather than leaving the app available only on my laptop or accepting an ongoing cost.

The final app uses a static React/Vite frontend on GitHub Pages and Supabase Free for authentication and PostgreSQL. The change is documented in the [free-hosting migration prompt](./prompts/free-hosting-migration.md) and [PR #2](https://github.com/CarmineCostoya/contact-cadence/pull/2). This was not just a hosting substitution. It moved the privacy boundary from Express route handlers into PostgreSQL Row Level Security policies. Every private table now has a policy tied to the authenticated Supabase user, and nested records such as interactions and contact tags verify ownership through the parent contact. The frontend uses the public anonymous key, while the database decides which rows that signed-in user may access. I learned that a public client key is safe only when database authorization is correctly designed and tested; hiding a key is not a substitute for access control.

Most user-facing features remained close to the plan: accounts, contact CRUD, interactions, stars, search, filters, sorting, dashboard statistics, follow-up reminders, tags, and CSV export all shipped. Some implementation details changed. Dashboard summaries are calculated from the user’s RLS-protected rows instead of an Express endpoint, and CSV is generated in the browser instead of on a server. These changes reduced infrastructure without reducing the intended experience. The completed Plan vs. Reality table in `PLAN.md` records each difference.

The development process also taught me that repository evidence matters independently from working code. Some early feature work was consolidated into local merge commits, so it did not produce one visible GitHub pull request per feature. I corrected the workflow for the final work by using public Issues, a dedicated branch, a saved prompt, a focused PR, and a merge for each change. Examples include the required test evidence in [PR #13](https://github.com/CarmineCostoya/contact-cadence/pull/13) and [PR #14](https://github.com/CarmineCostoya/contact-cadence/pull/14), plus the stranger-test corrections in [PR #6](https://github.com/CarmineCostoya/contact-cadence/pull/6), [PR #15](https://github.com/CarmineCostoya/contact-cadence/pull/15), and [PR #16](https://github.com/CarmineCostoya/contact-cadence/pull/16). My main learning is that architecture, cost, privacy, and development evidence have to be considered together from the beginning, not only when the app is ready to deploy.

## Reflection 2 — Stranger test findings and response

The stranger test identified three concrete areas where the app did not fully match a new user’s expectations. First, the tester asked whether Google authentication could be offered as an alternative to email and password. Second, the tester said the date a contact was met usually needs only a month and year, not an exact day. Third, the tester could not find a clear way to connect a contact to a tag while creating that contact. These observations were useful because all three features made sense to me as the builder, yet the tester exposed where the interface or scope did not match ordinary behavior.

I prioritized the tag problem first because it blocked a core organization workflow. Previously, tags could be assigned only after opening an existing contact, even though the contact form and tags feature were both already present. In [PR #6](https://github.com/CarmineCostoya/contact-cadence/pull/6), I added a visible tag picker directly to both the create and edit forms. The form explains what tags do, lists reusable tags as checkboxes, and links to tag management when none exist. This correction reduced an unnecessary save-open-edit sequence and made the relationship between contacts and tags discoverable at the moment the user needs it.

I also implemented the month-and-year feedback in [PR #15](https://github.com/CarmineCostoya/contact-cadence/pull/15). The Date met control now asks for a month and year, and the detail page displays a readable value such as “October 2026.” I kept the existing PostgreSQL date column to avoid a risky migration. A newly selected month is stored as its first day, while an existing exact date is preserved when the user saves without changing the month. Focused tests cover both cases. This solution improves the interface while protecting existing data.

While reviewing interaction history, I found one related usability gap: a mistaken interaction could be deleted but not corrected. [PR #16](https://github.com/CarmineCostoya/contact-cadence/pull/16) added an Edit action that prefills the existing interaction form and saves through the owned PATCH route. Although this was not one of the tester’s three original comments, it followed the same principle: users should be able to correct ordinary entry mistakes without deleting and recreating data.

I deferred Google authentication from version 1. Supabase supports OAuth, but enabling it responsibly requires a Google Cloud OAuth application, redirect-URL configuration, provider credentials stored outside the repository, and deployed login testing. It would also expand the scope after the app’s required email/password authentication was already working. I recorded it as a future improvement instead of rushing a partially configured login option before submission. The stranger test taught me to separate high-value, low-risk interface corrections from changes that introduce new external configuration and security responsibilities. It also showed why observation and notes are enough for this exercise: the value came from the exact points of hesitation and the concrete fixes they suggested, not from recording the tester’s screen.
